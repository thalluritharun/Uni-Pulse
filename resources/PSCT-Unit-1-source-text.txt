UNIT I – Problem Understanding and Representation

   1. Problem Identification and Framing

   3. Constraints and Assumptions
   4. Problem Decomposition

   6. Structured Problem Representation



This unit explains how to understand a problem clearly, identify what needs to be
solved, determine requirements and limitations, divide a complex problem into
smaller parts, identify relevant information, and represent the problem in a
structured way.


Learning objective:
By the end of this unit, students should be able to understand a problem before
attempting to solve it, especially when developing algorithms, programs, or
engineering solutions.


1. Problem Identification and Framing
1.1 What is a problem?
A problem is a situation in which we want to achieve a goal, but the method to
achieve that goal is not immediately clear.
Simple examples
      A student wants to improve examination marks but does not know how to
       plan their study.
      A college wants to reduce canteen waiting time.
      A program needs to find the largest number in an array.
      A farmer wants to reduce water usage in agriculture.
In each case, there is a current situation and a desired outcome.


1.2 What is problem identification?
Problem identification is the process of recognizing and understanding what is
wrong, missing, inefficient, or needs improvement.

                                        1
<PARSED TEXT FOR PAGE: 2 / 32>
Example: College Canteen
Current situation:
      Students wait a long time to purchase food.
      Several students arrive during the lunch break.
      The available counters may not serve everyone quickly.
Identified problem:
"Students experience long waiting times in the college canteen during lunch
hours."
Notice that the problem is stated clearly without immediately assuming that
adding more counters is the only solution.


1.3 What is problem framing?
Problem framing means expressing the identified problem in a clear and focused
way so that the correct problem is addressed.
A poorly framed problem can lead to an ineffective solution.
Poor problem framing
"The canteen needs more counters."
This assumes a solution before investigating the cause.
Better problem framing
"Students experience long waiting times during lunch because the ordering and
serving process may not handle peak demand efficiently."
This identifies the problem and leaves room to investigate its causes.


1.4 Elements of a good problem statement
A good problem statement should explain:
   1. Current situation: What is happening now?
   2. Problem: What is wrong or needs improvement?
   3. Affected people or systems: Who experiences the problem?
   4. Desired outcome: What should change?
   5. Scope: Which part of the problem will be addressed?

Example: Student Marks
Problem statement:
"Students in a class are scoring below the expected level in mathematics. The
objective is to identify the main learning difficulties and develop a study-support
approach to improve their understanding."
This statement explains the current situation, problem, and objective without
assuming a single cause.

1.6 Steps for problem identification and framing
   1. Observe the situation.
   2. Identify the gap between the current and desired situations.
   3. Collect relevant information.
   4. Identify who is affected.
   5. Investigate possible causes.
   6. Write a clear problem statement.
   7. Confirm that the statement addresses the actual problem.
Programming example

      Current situation: An array contains several numbers.
      Goal: Identify the largest number.
      Input: An array of numbers.
      Output: The maximum value.
      Success condition: The output must be greater than or equal to every array
       element.

2. Requirements and Expected Outcomes
2.1 What are requirements?
Requirements describe what a solution must do, provide, or satisfy.
They help us understand what is necessary before designing a solution.
Example: Online Library System
Possible requirements:
      Students must be able to search for books.
      Students must be able to check book availability.
      Librarians must be able to add and update books.
      The system must protect user information.
If requirements are incomplete, the final system may not satisfy users' needs.


2.2 Types of requirements
A. Functional requirements
Functional requirements describe what a system should do.
Examples:
      Allow a student to log in.
      Search for a book.
      Calculate student attendance percentage.
      Generate examination results.
      Display the largest number in an array.
B. Non-functional requirements
Non-functional requirements describe how well a system should work or the
conditions under which it must operate.
Examples:
      The system should respond quickly.
      User information must be protected.
      The application should be easy to use.
      The system should work reliably.
      The application should support many users.

2.3 What are expected outcomes?
An expected outcome is the result that should be achieved after solving the
problem.
A good expected outcome should be clear and, when possible, measurable.
Example: Reducing Canteen Waiting Time
Expected outcomes might include:
      Reduce average waiting time.
      Reduce ordering errors.
      Improve student satisfaction.
      Maintain affordable operating costs.
Suppose the current average waiting time is 12 minutes and the target is 6
minutes.
The target is measurable: reduce average waiting time by 50%.
These are illustrative targets; actual targets should be based on collected data.

Many computational problems can be represented using the following structure:

      Processing: Add the marks and divide by 3.

2.5 How do we check whether requirements are satisfied?
We define success criteria.
Examples:
      The program returns the correct answer.
      The application meets the required response time.
      The system prevents unauthorized access.
      The solution stays within the budget.
      Users can complete the intended task successfully.
Key idea: Requirements describe what is needed; expected outcomes describe
what we want to achieve; success criteria explain how we will verify achievement.

3.2 What are assumptions?
An assumption is something we accept as true for the purpose of analysing or
solving a problem, even though it may not have been fully verified.
Assumptions help us proceed when complete information is unavailable.
Example: College Attendance
Suppose we are calculating attendance percentage.
We may assume:
      All classes have equal weight.
      The attendance records are accurate.

3.4 Boundary conditions
A boundary condition describes a special case at the edge of the allowed input or
operating range.
Boundary conditions are important because solutions that work for normal cases
may fail at the limits.
Example 1: Voting Eligibility
Suppose the rule is that a person can vote at age 18 or above.
      Age 17: Not eligible.
      Age 18: Eligible.
      Age 19: Eligible.
The age of exactly 18 is an important boundary case.
Example 2: Array
Suppose an array contains N elements.
      Empty array: N=0
      One element: N=1
      Multiple elements: N>1
An algorithm that finds the largest element must handle an empty array
appropriately rather than assuming an element exists.

3.5 Why must we identify constraints and assumptions?
They help us:
   1. Avoid unrealistic solutions.
   2. Estimate required time and resources.
   3. Identify missing information.
   4. Make decisions logically.
   5. Handle special cases.
   6. Reduce unexpected failures.
Practice example
A college wants to build a student-result portal.
Identify:
      Two constraints
      Two assumptions
      Two boundary conditions
Possible considerations include development time, budget, availability of student
records, zero students in a class, and a student with marks at the minimum or
maximum allowed value.


4. Problem Decomposition
4.1 What is problem decomposition?
Problem decomposition is the process of breaking a large or complex problem into
smaller, manageable subproblems.
A complex problem may be difficult to understand and solve as one large task.
Dividing it into smaller tasks makes the work easier to plan, implement, test, and
maintain.
Example: College Management System
Developing an entire college management system is a large task.
We can divide it into:
      Student registration
      Faculty management
      Attendance management
      Examination management
      Fee management

<PARSED TEXT FOR PAGE: 10 / 32>
      Timetable management
      Report generation
Each module can be designed and tested separately.


4.2 Why is decomposition useful?
1. Reduces complexity
Smaller tasks are easier to understand.
2. Improves planning
We can estimate the time and resources needed for each subproblem.
3. Supports teamwork
Different team members can work on different modules.
4. Makes testing easier
Each component can be tested independently.
5. Simplifies debugging
Errors can be located within a smaller part of the system.
6. Encourages reuse
A useful component may be reused in another project.

4.4 Decomposition in programming
Consider the problem of calculating the average of five subjects and determining
the result.
We can divide it into:
   1. Read five marks.
   2. Validate the marks.
   3. Calculate the total.
   4. Calculate the average.
   5. Determine the result or grade according to the given rules.
   6. Display the result.
Each step can be developed as a separate function if appropriate.


4.5 Top-down approach
The top-down approach starts with the complete problem and progressively
breaks it into smaller subproblems.
Example:
Student Result System
  |
  |-- Read Marks
  |-- Validate Marks
  |-- Calculate Total
  |-- Calculate Average
  |-- Determine Grade
  |-- Display Result
We start with the overall goal and move toward smaller tasks.


4.6 Important point: Decomposition and dependencies
Sometimes one subproblem depends on another.
For example:
      Marks must be entered before they can be validated.
      Marks must be validated before calculating the total.
      The total must be calculated before calculating the average.

Therefore, decomposition should identify not only the smaller tasks but also their
order and dependencies.


5. Abstraction and Relevant Information
5.1 What is abstraction?
Abstraction means focusing on the important details of a problem while ignoring
details that are not necessary for the current task.
It helps reduce complexity by concentrating on what matters.
Simple everyday example
When using an ATM, a customer generally sees options such as:
      Withdraw cash
      Check balance
      Change PIN
The customer does not need to understand every internal operation of the bank's
servers to withdraw money.
The interface provides the relevant operations while hiding unnecessary internal
details.
5.2 Example: Student Attendance System
Suppose we want to calculate a student's attendance percentage.
Relevant information:
      Classes attended
      Total classes conducted
For this calculation, the student's height, home address, favourite subject, and
blood group are not required.

5.3 What is relevant information?
Relevant information directly contributes to understanding the problem, making
a decision, or producing the expected result.
Example: Selecting a Laptop for Programming
Relevant information may include:
      RAM
      Processor
      Storage
      Battery life
      Price
      Software compatibility
Less relevant information may include the colour of the packaging, unless
appearance is an explicit purchasing requirement.
Relevance depends on the goal. A detail that is unnecessary for one problem may
be important for another.


5.4 Abstraction versus ignoring information
Abstraction does not mean ignoring every detail that appears unimportant at first.
It means identifying which details are necessary for the current purpose.
For example, in an attendance system:
      Student marks may be irrelevant to attendance calculation.
      Student identity is important when recording attendance.
      Privacy and access control are important when designing the complete
       system.
Good abstraction removes unnecessary complexity without losing information
essential to correctness, safety, or the requirements.

5.5 Levels of abstraction
A complex system can be understood at different levels.
Example: Online Shopping System
Level           Focus
High-level      Customer buys a product
Middle-level Search, cart, payment, order management
Low-level       Database queries, validation, network requests, algorithms


At a high level, we focus on the overall purpose. At a lower level, we examine
implementation details.
5.6 Benefits of abstraction
      Reduces complexity
      Improves understanding
      Helps organize information
      Makes design easier
      Supports modular development
      Helps us focus on the actual objective


6. Structured Problem Representation
6.1 What is structured problem representation?
Structured problem representation means expressing a problem in an organized
form so that it becomes easier to understand, analyse, communicate, and solve.
Instead of keeping the entire problem in our mind, we represent its important
elements using text, diagrams, tables, flowcharts, formulas, or models.
Why is it useful?
      Makes the problem easier to understand.
      Identifies inputs and outputs.
      Shows the steps required to solve the problem.
      Reveals relationships between components.
      Helps identify missing requirements.
      Makes it easier to communicate ideas to others.

7. Integrated Example – College Library Book Search
Let's apply all six Unit I topics to one real-world problem.
Problem
Students spend too much time searching for books in the college library.
1. Problem Identification and Framing
Students cannot easily locate the required books. The goal is to help them find
books quickly.
2. Requirements and Expected Outcomes
Students should search by book title or author and view availability and shelf
location. The expected outcome is faster book discovery.
3. Constraints and Assumptions
Constraints may include budget, available computers, and development time. An
assumption might be that the library has a digital or digitizable book catalogue.
4. Problem Decomposition
Divide the system into book data management, search, availability checking,
shelf-location display, and administration.
5. Abstraction and Relevant Information
Focus on book title, author, availability, and shelf location. Ignore unrelated
information for the basic search operation.
6. Structured Problem Representation
Represent the system using an IPO model, a flowchart for searching, and tables
for book records and search results.
The example demonstrates how understanding and representing the problem
provides a foundation for designing a practical solution.


A useful sequence to remember is:
Identify → Define → Specify → Constrain → Decompose → Abstract → Represent
→ Solve → Verify

20. Explain how to represent the problem of finding the largest of two numbers.
Answer:
      Problem statement: Given two numbers, determine which is larger.
      Input: Two numbers, A and B.
      Process: Compare A and B.
      Output: Display the larger number or indicate equality.
Pseudocode:
START
   Read A, B
   IF A > B
     PRINT "A is larger"
   ELSE IF B > A
     PRINT "B is larger"
   ELSE
     PRINT "Both are equal"
   END IF
STOP
The test cases should include A greater than B, B greater than A, and A equal to
B.
